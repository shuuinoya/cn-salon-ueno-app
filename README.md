# CN Ueno health & beauty（元サイトの保存版）

## 入口URL（起動後に開く）
**このパソコン（サーバーを起動しているMac）から：**
| サイト | 名前 | URL |
|---|---|---|
| お客様の予約サイト | CN Ueno health & beauty | **http://cn-ueno-health-and-beauty.localhost/** |
| 店舗用の管理画面 | CNsalon@board | **http://cnsalon-board.localhost/** ※ログイン必須 |

**ほかの端末（同じWi-Fi/LANのiPhone・iPad・別のPC・別のブラウザ）から：**
| サイト | URL |
|---|---|
| お客様の予約サイト | **http://cn-ueno-health-and-beauty.local/** |
| 店舗用の管理画面 | **http://cnsalon-board.local/** ※ログイン必須 |

「〜.local」の名前は、サーバー起動中にmDNS（Bonjour。macOS標準の`dns-sd`）で同じネットワークへ配信されます。Mac・iPhone・iPad・Windows 10以降・Android 12以降はそのまま開けます。名前で開けない端末は、起動時にターミナルへ表示されるIPのURL（例 `http://192.168.x.x/`、管理画面は `/cnsalon-board`）でも開けます。Wi-Fiを替えた後は F5 で再起動すると新しいIPで配信し直します。

**鍵マークつき（HTTPS）で開くには：** サーバーは443番でHTTPSでも配信しています（`https://cn-ueno-health-and-beauty.local/` など、上記すべての名前で有効）。ブラウザの「保護されていない通信」表示を消すには、各端末に一度だけローカル証明書（CN salon local CA）を入れます。手順は **http://cnsalon-board.local/https-setup** （このMacでは http://cnsalon-board.localhost/https-setup ）に、iPhone・Mac・Windows・Android別で書いてあります。証明書はこのMac上で自動生成され（`tls/`。gitやzipには含めません）、このパソコンのサイトにしか効かないので他サイトの通信には影響しません。証明書を入れない端末は今までどおり http:// で使えます。

どちらも**数字のない、サイト名だけのURL**です。開いた後もアドレスバーに名前が残ります（転送されません）。
このMac上では、番号つきの http://127.0.0.1:5520/cn-ueno-health-and-beauty ／ http://127.0.0.1:5520/cnsalon-board も使えます。

**インターネット公開（どのネットワークからでも）**：`tools/bin/cloudflared`（Cloudflare公式トンネル）があると、起動時に**予約サイトのインターネット公開URL**（`https://〜.trycloudflare.com`・正式な鍵マークつき）を自動発行します。お客様は携帯回線でも自宅でも、どこからでもこのURLで予約できます。URLは起動のたびに変わり、ターミナルと `data/tunnel-url.txt` に表示されます。**管理画面・管理APIはインターネットには一切公開されません**（トンネル経由の接続はCloudflareの実IPヘッダで「外部」と判定され、予約サイト以外は403。流量制限もお客様の実IP単位で機能）。`DEMO_TUNNEL=0` で無効化できます。※固定の店名URL（独自ドメイン）にしたい場合はCloudflareアカウントとドメインの取得が必要です

**公開範囲**：お客様の**予約サイトは誰でも開けます**（ログイン・証明書は不要。流量制限つき）。**管理画面と管理APIは店内ネットワーク（このMacと同じWi-Fi/LAN）からしか到達できず**、さらにログインと権限のサーバー側検証がかかります。将来ルーターのポート開放やトンネルでインターネットに公開しても、外から届くのは予約サイトだけで、管理系にはネットワーク的に到達できません。

管理画面は**ID・パスワードでのログインが必須**です。アカウントは管理画面の「店舗情報→ユーザ情報（アカウント管理）」で管理者が追加・停止・権限変更できます（初期管理者のパスワードを変える場合もこの画面から）。未ログインで管理ページを開くとログイン画面に戻され、誤入力はエラー表示、ログアウトで再び施錠されます。予約サイト・マイページ・お客様用APIには影響しません。

サイト名は配信時に付け替えています（保存ファイル自体は無加工のまま）。予約サイトの画面・確認メールの件名は「CN Ueno health & beauty」、管理画面のログイン・各ページのタイトルは「CNsalon@board」で表示されます。

## セキュリティ（個人情報・予約情報・会社情報の保護）
**接続の範囲（二層構え）**
- **お客様の予約サイト（予約ページ・予約/回数券API・静的ファイル）は誰でも開けます**。管理系（`/admin`系ページ・`/api/demo/*`・`/api/partner/*`）は、このパソコンと**同じネットワークのプライベートIPからのみ**到達でき、インターネット側のアドレスからは即403。IP制限は多重防御の1枚目で、その内側でもログイン・権限検証が必ずかかります
- **流量制限**：このパソコン以外の接続元には、IPごとに「全体300回/30秒」「予約・回数券などの書き込みとログイン試行40回/5分」の上限があり、超過は429で拒否（自動連打・総当たり・大量予約スパムへの防御。通常の閲覧・予約では届かない量です）
- 予約・顧客・シフトなどのデータは**サーバーのメモリ上のみ**（Single Source of Truth）。どの端末から開いても、同じ最新データが表示されます（サーバー再起動で初期状態に戻ります）

**認証・権限（URLを知っているだけでは、何も見えない・できない）**
- 管理画面のページと管理API（`/api/demo/*` 等）は、**すべてサーバー側でログインと権限を検証**します。画面をフロント側で隠すだけの作りではありません。未ログインは401／権限外は403
- 権限は **管理者（admin）＞マネージャー（manager）＞スタッフ（staff）** の3段階（RBAC）。アカウント管理は管理者のみ、店舗設定・メニュー/回数券プラン編集・日報・スタッフマスタ編集はマネージャー以上、台帳の日常操作（予約・シフト・受付停止・転記リスト）はスタッフから使えます
- アカウントは「店舗情報→ユーザ情報（アカウント管理）」で追加・停止・権限変更・パスワード再設定。**停止・削除・降格は既存のログインにも即時反映**され、有効な管理者が最後の1人になる変更は拒否されます
- パスワードは平文で保持せず**ハッシュのみ**。ログインの連続失敗は一時ロック（総当たり対策）。認証イベント（成功・失敗・権限外アクセス）は機密を含まない形で記録され、アカウント管理画面で確認できます
- セッションは**端末ごとに独立**（ログインごとにCookie `HttpOnly`＋`SameSite=Lax` の乱数トークンを発行、7日で失効）。複数端末から同時に使え、ログアウトはその端末のセッションだけを失効させます

**お客様側データの保護（IDOR対策）**
- 予約の照会・キャンセルは予約IDだけでは不可で、**予約ごとの推測不能トークン**が必要（不一致は404）。回数券も券ID＋トークンの組でのみ照会・利用でき、他人の券は取得も利用もできません
- 回数券の残数・会員判定などは**常にサーバー側の値**で判定します（端末のlocalStorage等を書き換えても影響しません）。残数の減算は原子的・冪等で、複数端末から同時に操作しても二重消費・二重予約・マイナス残数は起きません
- 未ログインの予約サイトに返す設定情報はフォーム表示に必要な項目のみ（店舗マスタ・業務設定の中身はログイン済み管理画面だけが取得）

**通信・その他**
- **Hostヘッダ検証**（DNSリバインディング対策）：許可した名前以外のホスト経由のアクセスを403で遮断します
- **Origin検査**（CSRF対策）：悪意ある別サイトのページからの予約作成・設定変更などの書き込みを403で遮断します
- **セキュリティヘッダ**：`X-Content-Type-Options: nosniff`／`X-Frame-Options: DENY`（他サイトへの埋め込み禁止）／`Referrer-Policy: no-referrer`（参照元を外部へ送らない）
- 外部のCDN・解析タグ等への通信はありません（画像・JS・CSS・フォントはすべてローカル配信。元サイトのCloudflareボット判定コードも除去済み）
- ホットペッパー連携の受け口（`POST /api/partner/hotpepper`）はこのパソコン上からのみ受け付けます（本番では連携先のAPIキー検証に相当）
- **HTTPS（443番）**：このMacで自動生成するローカルCA（`tls/`・git/zip対象外）による証明書つきで、全URLがHTTPSでも開けます。CAを信頼させた端末は鍵マーク表示（手順: `/https-setup`）。CAの秘密鍵はこのMacから出ません。認証情報はURLに載せず、CookieはHttpOnly。インターネット公開時は正規CA証明書のHTTPS終端の下へ置く前提です
- **複数端末のリアルタイム同期**：台帳などの画面はサーバーへ数秒間隔で照会しており、別の端末（別ブラウザ・iPhone等）での予約・シフト・受付停止などの変更は、開いたままの画面にも数秒以内に自動反映されます（リロード不要）

元サイト https://cn-salon-ueno.cnsalon2021.chatgpt.site を、2026年9月24日時点のまま保存したものです。
`pages/` と `public/` の中身は基本的に元サイトのままです。例外は、追加したページ（demo-admin.html・pm-login.html・not-found.html）と、予約確認・完了ページのラベル折り返しバグを直すために最小修正した3ファイル（BookingText-*.js・page-WafCof8Y.js・page-ChO0-Npx.js）です。

## このMacで本番を動かす（Render が使えない間）
- **2026-10-19から、本番はデスクトップのiMac（CNdeiMac・利用者 cnsalon）で動いています**。本番用フォルダは iMac の `~/CNsalon本番（移動禁止）`（Codex の作業フォルダ `~/Desktop/cn-salon-ueno` とは別。**移動・削除・名前の変更をしない**。デスクトップに置くと裏側の本番がmacOSの保護で読めないことがある）。MacBook は作業用
- **本番は1台だけ**：起動プログラムは、そのMacの Tailscale の名前が公開URL（`cn-salon`）と同じときだけ本番を動かす。違うMac（今は MacBook＝`cn-salon-macbook`）で「このMacで本番を動かす.command」を押しても「起動しません」と出て止まる（2台で同じデータを上書きし合わないように）
- **本番への反映（iMac）**：作業したフォルダで commit・`git push origin main` → iMac の本番用フォルダで `git pull --ff-only origin main`（MacBook からは `git push cnsalon@CNdeiMac.local:CNsalon本番（移動禁止） main:refs/heads/incoming` → iMac で `git merge --ff-only incoming && git branch -D incoming`）。`server.js`・`demo-api.js`・`persist.js` を変えたときは、iMac で `kill -TERM $(pgrep -f '^/usr/local/bin/node server.js$')`（約5秒で同じURLのまま戻る）。`public/` の中は反映した瞬間に届く
- **本番のMacを移すとき**（例：iMac→MacBook に戻す）：①今の本番を「このMacの本番を止める.command」で止める（最後の保存がディスクとGitHubに入る）②`data/mac-production-state.json` を新しいMacへ写して中身（sha256）を照らし合わせる ③今のMacの Tailscale の名前を変え（`tailscale serve reset`・`tailscale set --hostname=別の名前`）、新しいMacを `tailscale set --hostname=cn-salon` にする ④新しいMacで「このMacで本番を動かす.command」。公開URLの設定（Funnel）は起動プログラムが自動で行う。⑤外からの確認は `curl --resolve cn-salon.taila11357.ts.net:443:$(dig +short @8.8.8.8 cn-salon.taila11357.ts.net | head -1) https://cn-salon.taila11357.ts.net/api/tickets/plans`
- 「**このMacで本番を動かす.command**」をダブルクリック。本番は**Macの裏側（launchd：`jp.cnsalon.production`）**で動き、**ターミナルやVS Codeの画面を閉じても止まりません**。URLは固定（Tailscale：`tools/mac-production.env` の `PUBLIC_URL`）
- サーバーが止まっても、見張り役（`tools/mac-production.js`）が3秒後に起動し直します（何度も止まるときは1分おきに起動し直し続ける。見張り役は自分からは終わらない）
- 止めるときは「**このMacの本番を止める.command**」（**Render に戻す前は必ず止める**。止めるとログインしても自動では始まりません）
- **Macを再起動したあと**は、ログイン時に自動で始まる設定ですが、このMacでは裏側の自動起動が後回しにされることがあるため、開けないときは「このMacで本番を動かす.command」をダブルクリック（確実に起動します。もう動いていれば何もしません）

## データの保存（永続化）と復旧
- 予約・顧客・シフト・回数券・メニュー・店舗設定・アカウント・ログイン中セッションは、**`data/state.json` に自動保存**されます（変化があったときだけ・原子的置換）。サーバー再起動・PC再起動・ブラウザ終了後も、どの端末から開いても同じ最新データが復元されます
- **保存のタイミング**：予約・スタッフ情報・シフト・設定・会員情報などを変える操作（GET以外のAPI）は、返事を返した直後に保存（続けて変えたときは60msまとめて1回）。メール送信の記録など操作以外の変化も1秒ごとの見回りで保存。一時ファイルを**ディスクへ書き終わる（fsync）のを待ってから差し替える**ので、変更の直後にパソコンを閉じる・電源が落ちる・強制終了しても消えない（変更から0.15秒で kill -9 しても残ることを確認済み）
- 保存のたびに直前の版が `data/state.json.bak` として1世代残ります。ファイルが壊れていた場合は自動で `.bak` から復旧し、壊れたファイルは `.broken-日時` に退避します（システムは止まりません）
- データファイルは所有者のみ読み書き可（0600）。gitにもzipにも含まれません
- **開発・テストとの分離**：`PORT` を指定した起動（テスト用 5530/5540 など）は初期データで動き、本番データに触れません。`DEMO_PERSIST=1`（保存を強制ON）／`DEMO_EPHEMERAL=1`（強制OFF）／`DEMO_DATA=パス`（保存先変更）で明示的に切り替えられます
- 全データを初期状態に戻したいときは、サーバー停止中に `data/` フォルダを削除してください

## ホットペッパー連携（デモ）
店舗情報メニュー→「ホットペッパー連携」。ホットペッパー側で入った予約を `POST /api/partner/hotpepper` で受け取り、**この台帳の同じ枠を自動で埋めます**（氏名・メニュー名・料金も反映、枠にはHPバッジ）。
- 空き判定は自社予約と**同一の統一ロジック**（シフト・休憩/業務・既存予約・鍵・対応メニュー・性別）を通すため、自社の予約サイトと**枠が被ることはありません**（埋まっていれば slotTaken で自動拒否）
- 同じ予約番号の再送は重複登録せず、HP側キャンセル（`action:"cancel"`）で枠を開放します。受信履歴は連携ページで確認できます
- **サロンボードへの反映（自社→HP方向）**：当システムに予約・変更・取消があると、連携ページの「転記待ちリスト」に自動で載ります。ワンクリックで転記用テキストをコピーしてサロンボードに登録し「反映済み」を押す運用で、HP側の枠も確実に塞げます（HP由来の予約は対象外）。※サロンボードは公開APIが無く、ID/パスワードでの自動書き込みは利用規約違反（アカウント停止リスク）のため行いません。完全自動の双方向連携はリクルート認定サービス（かんざし等）の契約が正規ルートです
- 実運用ではホットペッパー（サロンボード）側から本エンドポイントへ通知する接続が必要です。ローカルデモのため、連携ページの「受信テスト」で通知を疑似送信して動作確認できます
- **予約通知メールの自動取り込み（実接続）**：ホットペッパーには公開APIが無いため、サロン宛に届く「予約通知メール」を取り込む方式にも対応しています。`mail-config.json` の `hotpepper.enabled` を有効にすると、同じGmail（IMAP）の受信箱を**毎分自動チェック**し、件名に `subjectFilter` を含む通知メールを解析（予約番号・来店日時・メニュー・料金・氏名・電話）して台帳に反映します。連携ページの「メール取込を今すぐ実行」で手動実行も可能。同じメールを何度読んでも予約番号で重複登録を防ぎます（実際のGmail往復での自動取込を検証済み）

## 回数券（チケット）
メニュー管理と同じ操作感で回数券を販売・管理できます。**残り回数の整合性が最重要仕様**です。
- **管理（店舗情報→回数券管理）**：通常メニューとは完全に独立した専用画面。プランごとに1枚のカードで、予約サイトの表示に合わせて細かく設定できます：**名称・価格・通常価格（任意。予約サイトで取り消し線の割引表示）・回数（1〜200）・有効期限（購入日から1〜60か月。既定12か月＝1年間）・説明文・対象メニュー・復活の組・購入時の復活・販売する（マイページで購入可）・予約/メニューページ最上部に表示・表示順（↑↓）**。入力中に「予約サイトでの表示」のプレビューが変わります。有効期限の変更はこれから購入される券に適用され、購入済みの券の期限・対象メニューは購入時のまま変わりません（月末・うるう年も日本時間で計算）。予約/メニューページ最上部の**見出し**とマイページの**購入欄の案内文**も編集できます
- **購入（マイページ→回数券）**：**ログイン中の会員のみ購入可能**（サーバー側で必ず判定）。未ログインにはログイン／会員登録を案内します。購入した券は購入者本人の会員アカウントに自動で紐付き、他人の券はURLやIDを操作しても見えず使えません。会員には【予約】【メニュー】ページの最上部にも回数券（残り回数・購入導線）が常に表示されます
- **残り回数のお知らせメール**：回数券を**1回使うたび／返却のたび**に「残り回数のお知らせ（あとN回）」メールを本人へ自動送信（券名・残り回数・有効期限・マイページへの案内）。残り回数はマイページの「回数券」タブでいつでも確認できます
- **期限前リマインド**：有効期限の**30日前（既定）**に自動でリマインドメールを送信します。タイミングは「回数券管理」で**60日前・30日前・14日前・7日前・3日前・前日から複数**選べます（その日の10:00以降に送信）。本文：お名前・回数券名・残り回数・有効期限（復活分は内訳）・予約サイトのURL・マイページのURL
  - 対象は**未使用回数が1回以上残っている券だけ**（使い切り・期限切れ・復活済みには送りません）。送信の直前に最新の残り回数・有効期限・会員情報を読み直し、意味がなくなっていれば「送信中止」と理由を記録します
  - 重複防止：券ごとに「どの有効期限の・何日前の通知か」を送信記録（remind_log）へ先に書くため、処理が何度・どこから実行されても**同じ券・同じ期限・同じタイミングには1通だけ**。期限が変わった（延長・復活）場合は新しい期限で送り、**古い期限に基づく通知は再送でも送りません**。停止などで複数のタイミングをまとめて過ぎたときは、期限に一番近い1通だけ送ります（残りは「省略」と記録）
  - 送信履歴：会員ID（会員のメールアドレス）・回数券ID・有効期限・通知タイミング・送信日時・結果・失敗理由。「回数券管理」の各券に予定日時と状態、［メール］に履歴が出ます。**送信失敗は［再送する］で1回だけ再送**できます（メール管理からも可。再送中・再送済みのものは重複して作りません）
  - 実行：**サーバー内で毎分**（`setInterval`。画面を開いていなくても動きます）。無料ホスティングの休止に備え、環境変数 `CRON_SECRET` を設定すると `/api/cron/tick?key=<CRON_SECRET>` を外部のCron（cron-job.org・GitHub Actions・Render Cron Job など）から10〜15分おきに呼んで同じ処理を実行できます（未設定なら404）。最終実行時刻は「回数券管理」に表示されます
- **期限切れ分の復活**：会員が回数券を購入すると、その会員の回数券のうち**購入の時点で有効期限が切れていて未使用回数が残っているもの**から、**同じ「復活の組」かつ同じ「対象メニュー」の券だけ**を探し、未使用回数を**「復活分」の回数券（別の券）**として使えるようにします。有効期限は**新しい購入日から1年間**（新しい購入と同じ）
  - 例：10回券を6回使って期限切れ（残り4回）→ 10回券を購入 → 新しい10回券（10回）＋「回数券 10回券（復活分）」（4回）。購入回数に足して表示はしません
  - 記録：元の券は購入回数・利用回数・有効期限をそのまま残し、残り回数を0にして「復活（新しい券へ移動）」として**何回をどの券へ移したか**を履歴に残します（状態「復活済み」）。復活分の券は**どの購入分から何回復活したか**、購入した券は**この購入で何回復活したか**を持ちます。マイページ・管理画面・購入のご案内メールに内訳を表示します
  - 条件はプランごとに「回数券管理」で設定：**対象メニュー**（すべて／指定したメニューのみ。予約時にサーバー側で判定）・**復活の組**（同じ組名どうしで復活。空欄はそのプランどうしのみ。標準の5・10・20回券は `standard`）・**購入時に復活するか**。使い切りの券・種類や対象メニューが違う券・期限内の券は復活しません
  - 二重防止：購入は**購入キー**（requestKey）で、再読み込み・再送信・APIの再実行でも同じ結果を返します。復活は購入ごとに1回だけ（何度実行しても同じ回数）。購入と復活は1つの処理で、途中で失敗したら**購入ごと取り消して元に戻します**（回数だけ増える・購入記録だけ残る、を防止）
  - 会員以外（予約実績のあるメールでの購入）は自動では復活しません（なりすまし防止）。管理画面の［復活確認］で店舗が実行できます
- **利用**：予約フォームで「使用する回数券（残N回・期限）」を選択。予約が確定した瞬間に**サーバー側で1回分を原子的に減算**します（検証→予約成立→減算まで同一の同期処理。フロントの残数表示は一切信用しません）
  - 残0・期限切れ・購入者本人（メール一致）以外はサーバーが拒否
  - **残り1回で同時に2件予約しても、成立は1件だけ**（もう1件はticketEmptyで拒否、残数は0で止まりマイナスなし）
  - 同じ予約への二重消費は予約ID単位の冪等制御で防止（多重送信のrequestKey再送でも減りません）
  - 回数券利用時はコース料金が回数券払いになり、深夜料金・指名料のみ通常請求
- **キャンセル規定**：予約開始前の正規キャンセルに限り1回分を自動返却（1予約につき1回まで・履歴で冪等）。開始後の取消では返しません
- **表示**：完了画面・マイページ・管理台帳（券バッジ／詳細パネル／ホバー）で常に最新の残数を確認できます
- **メール**：回数券利用の予約だけ、確認・リマインド・変更・店舗通知・取消メールに回数券の状況を追記（通常予約のメールは一字も変わりません）。メール送信の成否と残数処理は分離しており、再送で減算されることはありません
- **メールの回数券情報は送信直前に作る**：回数券を含むメール（購入・残数お知らせ・期限リマインド・回数券利用の予約メール）は、本文を予約・購入の時点で固定せず、**送信する直前にデータベース（サーバーの回数券データ）から最新の残り回数・有効期限を読み直して作ります**。例：3日後の予約を残り4回の時点で入れ、その後に2回使えば、24時間前のリマインドには「あと2回」と載ります。本文には回数券名・購入日・残り回数・有効期限・ご利用状況（使える／使い切り／期限切れ）を必ず記載し、同じお客様が他にも使える回数券を持っていれば券ごとに並べます（取り違え防止）
- **送信記録**：メールごとに、送信先・送信日時・種類・対象の回数券・**送信時点の残り回数と有効期限**・送信結果・エラー内容を保存します。管理画面の「メール管理」で各メールの「送信時点の回数券情報」を、「回数券管理」の各券の［メール］で、その券について送ったメールの一覧と**送信時点の値が台帳（利用履歴）と一致しているか**を確認できます。送信処理中にサーバーが止まったメールは、二重送信を防ぐため自動再送せず「送信結果不明」として残ります

## お客様の会員ログインとマイページ（/mypage）
予約サイト右上の**「ログイン」ボタン**で、本物と同じ構成のログインモーダル（メールアドレス・パスワード・パスワードを忘れた方・新規会員登録・キャンセル。ソーシャルログインは費用がかかるため使いません）が開きます。同じログイン欄は**トップ・日時選択ページの右の列**にも表示され、ログイン中は会員メニュー（お名前・保有回数券の残り回数・マイページ・回数券・ログアウト）になります。**はじめての方は「新規会員登録（無料）」**（お名前・メールアドレス・パスワード・確認用パスワード）から登録でき、登録が完了すると**「会員登録完了のお知らせ」メール（ログインID＝メールアドレス入り）**が届き、そのままログイン状態になって【予約】【メニュー】の一番上に回数券が表示されます。ログイン欄で未登録のメールアドレスを入れた場合は、登録はせずに新規会員登録へ案内します（打ち間違いで別のアカウントができないように）。ログイン中は右上が「マイページ」になります。

- **予約情報**：予約中／取消済みの一覧、**「日時を変更」**（会員のみ。予約フローへ進み、新しい日時で確定した瞬間にサーバーが元の予約を自動取消。回数券利用分は返却→再使用）、**予約取消**（管理画面の台帳・空き状況へ即時反映、取消メールも生成）

- **回数券**：保有券の残り回数・有効期限、販売中プランの購入（入力なし・店頭払い）
- API：`/api/member/login`（登録兼用）・`logout`・`me`・`profile`・`reset`。本人確認はすべてサーバー側（他人の予約・券は見えず操作できません）

## スタッフ紹介（/staff・上部の【スタッフ】タブ）
上部（スマホは下部）のメニューの【メニュー】を【スタッフ】に替え、スタッフ紹介のページ（`pages/pm-staff.html`）にしました。メニューの一覧は【予約】の最初の画面で見られます（`/menus` のページもそのまま開けます）。

- 指名つきのメニュー選択は速く出るよう、サーバーがページを返すときに「そのスタッフが担当できるメニューだけを表示する指定（CSS）」とスタッフの情報（`window.__cnNom`）を最初から入れておく（絞り込む前の一覧が一瞬見えることもない。指名スタッフの表示は画面の準備ができしだいすぐ）

## お客様の予約（動くようにしてあります）
日時選択ページの空き状況・スタッフ指名・予約の送信も、管理画面と同じ架空データで動きます。
お客様の予約もそのまま通せます。

- 休憩・業務の登録は、時間（分）ボタンの下の自由入力欄で5〜1020分まで任意の分数を指定できます
- 空き状況の○×は、管理画面の**シフト・休憩/業務・既存予約・対応メニュー・受付停止**から計算されます
- スタッフ情報の**対応メニュー（チェックボックス）**は、指名あり・指名なしの両方の担当決定に完全連動します。チェックのないメニューのスタッフは候補から除外され、画面を直接操作してもサーバー側の再チェックで拒否されます。チェックを外したメニューに今後の予約が残っている場合は、予約は維持したまま管理画面に警告が出ます
- スタッフ指名（指名料）は、スタッフ情報の**個人指名・指名料**の設定が反映されます。料金・指名料は**予約確定時点の値**で保存され、あとから設定を変えても過去の予約は変わりません
- 複数名の予約は、人数分の対応可能スタッフをまとめて確保します（担当変更・取消時も全員分を更新）
- 予約の担当変更（別スタッフへ移動）は、変更先の対応メニュー・シフト・休憩・既存予約を再確認し、指名予約は**変更先の指名料で再計算**されます
- 上部メニュー「店舗情報 → 店舗情報」で、予約フォームの**フリーメッセージ欄**（表示／必須／見出し／placeholder／説明文／文字数制限）を設定でき、予約サイトへ即時反映されます。入力内容は台帳・通知メールまで届きます
- 「店舗情報 → メニュー一覧」で**メニューの追加・変更・削除・写真の登録**ができます。空き状況・予約金額・管理画面の予約フォームの選択肢に即時反映されます（予約が入っているメニューは削除不可。料金変更は新規予約のみに適用され、確定済み予約の金額は変わりません）。予約サイトのメニュー紹介ページの写真25枚が最初から各メニューに登録済みで、「写真変更／写真削除」から差し替えできます（メニュー・写真の変更は保存され、再起動しても残ります）
- 「日次管理 → 営業実績」で、本日の売上・来店数・オンライン予約数・シフト状況・明日の出勤スタッフなどを**予約とシフトの実データから自動集計**した日報画面が見られます（天気・実施プラン・担当者の一時保存／日報送信つき）
- お客様が予約すると、**管理画面の予約台帳にその場で表示**されます（逆に、台帳で予約を取り消せば枠が空きます）
- 予約完了ページの予約番号・合計金額も本物と同じ流れで表示されます
- 予約の完了・変更・取消時に、お客様宛と店舗（管理者）宛のメールを自動生成します（実際には送信せず、 http://127.0.0.1:5520/admin/mails で件名・本文・送信状態まで確認できます）。件名・本文・改行は本物のメールと同じ書式（ご予約内容確認／ご予約リマインド／ご予約キャンセルのご案内、店舗専用版つき）で、本文のキャンセルリンクからマイページに入れます。各メールは**実際に届く形のHTMLメール**（テーブル＋インラインCSSのみのメールクライアント互換構造・スマホでも崩れない600px幅）としても生成され、メール管理画面でGmailと同じ見た目のプレビューを確認できます
- **リマインドメール（来店前のご案内）**：予約完了メールの使い回しではなく専用の文面です。送信時刻は**お客様＝来店24時間前**（24時間を切ってからの予約は予約直後）、**店舗＝来店日の9:00**。本文は予約時に固定せず、**送信する直前にその予約の最新データから作ります**：お客様名・日時（開始〜終了・施術時間）・予約ID・メニュー・人数・担当スタッフ（台帳の現在の担当、指名は「ご指名」）・料金内訳（コース料金・指名料・深夜料金・合計＝予約の合計金額）・お支払い（利用規約どおり：店頭払い、現金以外は5％の決済手数料）・ご来店場所と地図・予約サイトの「ご来店に際しての注意事項」・変更/キャンセルの案内・マイページへの直接リンク、回数券利用時は送信時点の残り回数と有効期限
- **リマインドを送らない条件**：送信直前に、取消済み／来店時刻を過ぎた／同じ予約・同じ日時のリマインドが送信済み、のいずれかなら送らず「送信中止」（理由つき）として記録します。予約日時が後ろへ変わっていれば、新しい来店24時間前まで自動で待ちます。管理画面の「失敗メールを再送」を押しても、この確認は必ず行われます
- **メール内のURL**：公開ドメイン（本番は Render の公開ホスト名＝https://cn-salon-ueno.onrender.com、独自ドメインは環境変数 `PUBLIC_HOST`／`PUBLIC_ORIGIN`）から作ります。127.0.0.1・localhost 等の開発用URLを含むメールは実送信しません（ローカルから実送信テストをする場合は mail-config.json の `publicOrigin` を設定）。「予約のキャンセルはこちら」のリンクは、**ログイン不要でマイページのその予約へ直接移動**し、そのまま取消できます（日時変更・回数券は会員ログインが必要）
- **本番でメールを実際に届ける設定（Render の Environment）**：`MAIL_USER`（送信元Gmail）・`MAIL_PASS`（Gmailのアプリパスワード16桁）・`MAIL_SEND_TO_ALL=1`（お客様を含む全宛先へ送る）・`STORE_MAIL`（店舗宛て通知の受信アドレス。未設定なら「店舗情報」のメールアドレス宛て）。未設定の間はメール管理に記録されるだけで、実際には届きません。example.com 等のテスト用アドレスへは設定に関係なく送りません
- **Render（無料プラン）からの送信は「Googleの送信中継」を使う**：Render の無料プランはメール送信用の通信（SMTPのポート）を外に出せず、Gmailへ直接つなぐ送信は失敗します（実際に本番で確認）。そこで [tools/mail-relay.gs](tools/mail-relay.gs) を送信元のGoogleアカウントで Google Apps Script のウェブアプリとして公開し、Render の Environment に `MAIL_RELAY_URL`（ウェブアプリのURL）・`MAIL_RELAY_SECRET`（スクリプトの SECRET と同じ値）・`MAIL_SEND_TO_ALL=1` を設定します。設定されていればSMTPより優先して https で送ります（Gmail無料アカウントは1日100通まで）。送信に失敗したときは、メール管理に原因と対処が表示されます
- **送信中継は管理画面から登録できる（おすすめ）**：管理画面の「店舗情報 → メール送信設定」（/admin/mail-setup、管理者のみ。Google Apps Script のURL（script.google.com）だけ登録できます）で、合言葉入りのコードをコピー → Google Apps Script に貼り付けてウェブアプリとして公開 → URLを貼り付けて「登録してテスト送信」。Render の環境変数は変えなくてよく、登録すると店舗のアドレスにテストメールを送り、以後の予約完了・リマインド・店舗通知はすべて中継から全員宛てに送ります。登録内容は保存データ（GitHubの非公開データリポジトリ）に残るため再起動後も有効です。優先順位は mail-config.json → 環境変数の中継（正しいURLのとき）→ 管理画面で登録した中継 → 環境変数のSMTP
- **送れていないメールの表示**：送信設定がない・テスト用アドレスなどで実際には送っていないメールは、メール管理で「記録のみ（実際には届いていません）」と表示し、画面上部に理由と設定方法を出します。予約完了ページでも、実際に送れたときだけ「確認メールの送信を受け付けました」と表示します
- **新しい予約の通知（管理画面）**：予約サイト・ホットペッパーから実際に入った予約を、来店日時とお名前つきで右下に通知します（20秒ごとに確認・端末ごとに既読管理）。押すとその日の予約台帳へ移動します（以前の通知は実在しない予約を表示する飾りでした）
- **リマインドを時刻どおりに送るための稼働維持**：Render の無料プランは15分アクセスが無いと停止し、その間はリマインドを送れないため、本番では10分ごとに自分の公開URLへ軽くアクセスして停止させません（`KEEP_AWAKE=0` で無効化）
- **実際にGmailへ届けたい場合（任意）**：プロジェクト直下の `mail-config.json` を開き、Googleの「アプリ パスワード」（Googleアカウント→セキュリティ→2段階認証を有効化→アプリ パスワードで16桁を発行）を `pass` に貼って `enabled` を `true` にし、F5で再起動してください。**allowToに書いた宛先にだけ**SMTPで実送信されます（それ以外の宛先・店舗宛は従来どおりデモ内のみ）。送信状態は本物と同じく「送信予定→送信処理中→送信済み／送信失敗（エラー理由つき・再送信ボタンで再試行）」で管理されます。この設定ファイルはGit管理外で、パスワードがコミットされることはありません
- メールは「送信予定 → 送信処理中 → 送信済み／送信失敗」の状態で管理され、送信済みは配信サービスの成功応答を確認してから記録します。同じメールが二重送信されることはなく、取消した予約のリマインドは送信されません
- リマインドメールも自動登録されます（お客様＝来店24時間前、店舗＝当日朝9時）。予約変更時は変更後の内容で再登録されます
- データはメモリ上のみ。サーバー再起動で初期状態に戻ります

## 画面を開く・移動する速さ（2026-10-18 その2）
外（スマホの回線）から使うときに遅かったのは、画面を開くたびの「往復の回数」でした。往復を減らしています（見た目は同じ）。
- **画面の部品の版つきの場所**：`/_next/static/chunks|css/…` を、サーバーがページを返すときに `/_next/static/v-<版>/…` に書き換える（HTML・RSC・部品どうしの読み込み一覧。server.js の pinStatic）。版は部品フォルダの全ファイルの名前・大きさ・更新時刻と server.js の中身から作るので、**部品を1つでも書き換えると全部の場所が変わり、すぐ全員に届く**。今の版の場所は1年間確認なしで使い回す（immutable）。古い版の場所で頼まれたら今の中身を保存させずに返す。`?v=更新時刻` つきのファイル（会員ログイン・辞書・管理画面の上書きなど）も今の更新時刻なら1年。管理画面の上書きの版（pmVer）はサーバーの再起動なしで変わる
- **ページの先頭の小さな仕組み**（`public/cn-fast.js`。サーバーが全ページの先頭に直接入れる。書き換えるとすぐ反映）：
  - ページ移動の裏側の通信（`?_rsc=`）をやめて、すぐ次のページを開く（サーバーはその通信にも普通のページを返していたため、1往復むだだった）。画面に見えているリンク全部の先読み（メニュー一覧で約60〜130KB）もやめた
  - **ページと一緒に返すデータ**（server.js の pageBoot／apiPeek）：ページが開いた直後に必ず取りに来るデータ（予約サイト＝会員情報・フォームの設定・日時の空き状況・スタッフ一覧、管理画面＝その日の台帳・受付停止・設定・カレンダー・お知らせ・メニューなど）を、サーバーの中でブラウザから頼まれたときと同じ処理（同じログイン状態）で作ってページに入れる。開いて5秒間はそれを使い、書き込みの操作をしたら使わない。サーバーの「変わった」合図の番号（起動ごとの印つき）がデータを作ったときと違えば使わず取り直す
  - 同じデータを同時に何回も取りに行くときは1回の通信を分け合う
- 予約サイトはリンクに指が触れた（マウスを押した）瞬間に次のページを取りに行く（speculation rules・Chrome系）。辞書（cn-i18n.js）は予約サイト本体のページでは表示を待たせない（defer）
- ページごとの部品の先読みの指定を自動で付ける（入口の部品の一覧から。初めて開くときの1往復を省く）
- **管理画面のログイン画面**で、ID・パスワードを入れている間に台帳の部品を先に読み込む（`window.__cnWarm`）。台帳を開いた直後の「念のための全部取り直し」は、最初の合図がデータを作ったときと同じ番号なら省く
- 結果（スマホ回線相当・押してから使えるまで）：ログイン→台帳 約0.65秒→約0.25〜0.3秒（台帳を開いた直後のデータの取り直し 約15回→0回）／トップ→メニュー一覧 0.2秒→0.02秒／メニュー→日時 0.6秒→0.13秒／日時→入力画面 0.5秒→0.2秒
